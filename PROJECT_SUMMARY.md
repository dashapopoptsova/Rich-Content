# Проект «РИЧ-контент» (Rich-Content) — сводка

## 1. Цель и контекст

**Продукт (по ТЗ):** инструмент для селлеров — автоматическое или ручное формирование **вертикального РИЧ-контента** (одно длинное изображение-лендинг) для карточек товаров на маркетплейсах. Ключевой критерий качества: итог выглядит как **цельный баннер**, а не набор склеенных картинок.

**MVP-фокус:** один итоговый файл **PNG/JPG**, получаемый через **генерацию изображения** моделью **Google Gemini 3.1 Flash Image Preview** с провайдером **OpenRouter**, на входе — **3–10 изображений** товара, тексты на баннере **только с фактами с фото** (без выдуманных характеристик).

**Ограничения ТЗ (вход):** форматы JPG/PNG, до 5 МБ на файл, разрешение кратно **800×500 px**, 3–10 изображений.

---

## 2. Что реализовано

### 2.1. Логика и пайплайн

- **Сжатие изображений** перед отправкой в API, чтобы уложиться в **лимит OpenRouter / провайдера ~30 МБ** суммарного «скачанного» контента картинок; с учётом **base64 в JSON** фактический запрос тяжелее сырых байт на ~33%.
- **Промпт** на русском: структура Hero → преимущества → раскрытие → свойства → ассортимент; запрет на выдуманные цифры и состав; стиль «единый лендинг».
- **Параметры API:** модель `google/gemini-3.1-flash-image-preview`, `modalities: image + text`, `image_config` (например, соотношение сторон `1:4`, размер `2K`).

### 2.2. Python (основная разработка сейчас)

| Артефакт | Назначение |
|----------|------------|
| `generate_rich.py` | CLI: читает **`входные/`**, сжимает через **Pillow**, POST на OpenRouter, сохраняет результат в **`выходные/`** |
| `requirements.txt` | Зависимости: Pillow, requests, python-dotenv, certifi, truststore |
| `.env` / `.env.example` | Ключ `OPENROUTER_API_KEY`, опции TLS (ниже) |
| Папки **`входные/`**, **`выходные/`** | Входные карточки и готовый файл вида `rich-<timestamp>.jpg/png` |

Поддерживаемые расширения при сканировании папки: **`.jpg`, `.jpeg`, `.png`, `.jfif`**.

### 2.3. Веб и автоматизация (вспомогательно / исторически)

| Артефакт | Назначение |
|----------|------------|
| `upload.html` | Простая форма POST multipart на URL webhook n8n (без терминала для пользователя) |
| `n8n-rich-content-mvp.json` | Workflow: Webhook → проверка → HTTP OpenRouter → извлечение картинки → ответ |
| `n8n-code-build-payload.js` | Исходник логики для ноды Code в n8n (можно не использовать при работе только из Python) |

### 2.4. Документация по ТЗ

- `ТЗ.md`, `ТЗ РИЧ.txt` — постановка (режимы авто/ручной, типы блоков, нефункциональные требования).

## 3. С чем столкнулись (проблемы и решения)

### 3.1. n8n и бинарные данные

**Проблема:** в теле запроса к OpenRouter в `image_url` попадало `data:image/jpeg;base64,filesystem-v2` вместо реальных данных.

**Причина:** в новых версиях n8n бинарники часто хранятся **во внешнем хранилище**; поле `binary.data` — это **ссылка**, а не base64.

**Решение:** в Code-ноде читать байты через **`this.helpers.getBinaryDataBuffer(itemIndex, key)`**, затем собирать настоящий data URL.

### 3.2. Лимит «Downloaded image content cannot exceed 30MB»

**Проблема:** ошибка OpenRouter при суммарно большом объёме входных изображений.

**Причина:** лимит на стороне **API / провайдера**, клиентом **не увеличивается**. Усугубление: кодирование **base64** увеличивает объём тела запроса относительно «сырых» МБ файлов.

**Решение:** многоступенчатое **JPEG-сжатие и уменьшение длинной стороны** (в Python — Pillow; ранее в n8n планировался **sharp**) до целевой суммы байт (в коде закладывался запас, например порядка **~16 МиБ** суммарно после сжатия под лимит ~30 МБ с учётом base64).

### 3.3. Расхождение «24,5 МБ в проводнике» и `totalBytes: 25784439`

**Проблема:** пользователь видел ~24,5 МБ в проводнике, а в ошибке — ~25,78 млн байт.

**Объяснение:** это **одни и те же файлы**: 25 784 439 байт ≈ **24,58 МиБ**; проводник **округляет** и может показывать **МБ** в десятичной или двоичной системе.

Отдельно: без модуля сжатия в n8n действовал **внутренний порог** для «сырых» суммарных байт **ниже**, чем лимит API, чтобы не отправлять в API заведомо перегруженный запрос.

### 3.4. Отказ от n8n как основной платформы

**Причина:** невозможность настраивать Docker / ставить **sharp** в окружении n8n.

**Решение:** перенос основной логики на **локальный Python** с зависимостями в виртуальном окружении **`.venv`** (`pip install -r requirements.txt`), без контейнера.

### 3.5. SSL / корпоративная сеть

**Проблема:** `SSLCertVerificationError: unable to get local issuer certificate` при запросах к `openrouter.ai`.

**Причины:** корпоративный **SSL-инспекция**, свой корень CA; либо Python по умолчанию не использует то же хранилище, что браузер.

**Что сделано в коде:**

1. По умолчанию после установки зависимостей используется **`truststore`** — контекст TLS из **хранилища сертификатов ОС** (в т.ч. Windows).
2. **`certifi`** — запасной CA-bundle; можно принудительно через **`SSL_USE_CERTIFI=1`** в `.env`.
3. Явный путь к PEM: **`SSL_CERT_FILE`** или **`REQUESTS_CA_BUNDLE`**.
4. Крайний вариант (только если политика безопасности позволяет): **`OPENROUTER_INSECURE_SSL=1`** — отключение проверки сертификата.

## 4. Что делаем сейчас и что дальше

### Сейчас

- **Основной рабочий путь:** запуск **`python generate_rich.py`** из каталога проекта с активированным **`.venv`**, ключом **`OPENROUTER_API_KEY`** в **`.env`**, изображения в **`входные/`**, результат в **`выходные/`**.
- При ошибках TLS: **`pip install -r requirements.txt`**, при необходимости **`SSL_CERT_FILE`**, **`OPENROUTER_INSECURE_SSL=1`** или согласование с IT по корпоративному сертификату.

### Рекомендуемые следующие шаги (по ТЗ, вне текущего MVP)

| Направление | Комментарий |
|-------------|-------------|
| Валидация **800×500** для входных файлов | Проверка ширины/высоты в пикселях (Pillow) перед отправкой |
| **Ручной режим** и конструктор блоков | UI + хранение структуры блоков; не только «одна генерация моделью» |
| Веб-интеграция | Свой backend или статика + API вместо n8n webhook |
| Шаблоны по категориям (одежда, косметика и т.д.) | Отдельные промпты или пресеты |
| Экспорт нескольких размеров / форматов | Доп. постобработка |

### Артефакты, которые можно считать устаревшими для единственного процесса «только Python»

Если n8n больше не используется, можно не поддерживать **`n8n-rich-content-mvp.json`** и **`n8n-code-build-payload.js`**; **`upload.html`** остаётся полезным только при отдельном webhook-сервере.

## 5. Быстрый чек-лист запуска (Python)

```powershell
cd "<путь>\Rich-Content"
.\.venv\Scripts\activate
pip install -r requirements.txt
# Создайте .env по образцу .env.example, задайте OPENROUTER_API_KEY
python generate_rich.py
```

При успехе в консоль выводится путь к файлу в **`выходные/`**.

---

## 6. Безопасность

- **Не коммитьте** файл **`.env`** с реальным ключом API.
- Ключи, которые попадали в скриншоты или чаты, лучше **отозвать** в кабинете OpenRouter и выпустить новые.
